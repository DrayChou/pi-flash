# 083 项目搜索（文件 + 内容）

> 参照：Zed `crates/search` + `crates/project/src/project_search.rs` + `crates/file_finder`
> （基线 commit `4c902c9`，2026-09-23）。**无索引**——先取证再复刻。

## 1. 结论：Zed 不建索引（取证）

复刻前先把「它是不是靠索引」查实了，避免照抄一个不存在的架构：

| 问题 | 取证 | 结论 |
|---|---|---|
| 有倒排/trigram/全文索引吗 | 全仓 grep `tantivy`/`trigram`/`inverted index`/`fts5` 零命中 | 无 |
| spawn ripgrep 吗 | `rg`/`ripgrep` 在 Cargo.toml 与 crates 内零命中 | 无（自己用 `fancy_regex` 行级扫） |
| 内容搜索怎么走 | `project_search.rs`：路径候选 → glob 过滤 → `fs.open_sync` 读盘 → `query.detect()` 找首命中 → 命中的才开 Buffer 全扫 | 纯实时扫 |
| 文件名搜索怎么走 | `file_finder.rs`：`worktree.snapshot().files()` 内存文件树 + `fuzzy_nucleo` 匹配 | 有内存路径树（**非**内容索引，重启重建） |
| 唯一像索引的东西 | `edit_prediction_context/bm25_context.rs`：BM25，**按需构建、不落盘**，只服务编辑预测 | 与用户搜索无关 |

所以「复刻 Zed 的搜索」= 复刻一条**实时扫描流水线** + 一套**结果面板版式**，不是复刻检索索引。

## 2. 与 Zed 的结构差异（为什么可以更好）

Zed 的两阶段（先磁盘粗筛首命中、再开 Buffer 精算）是被它的编辑器内核逼出来的：精算必须
经过 `Buffer`/`MultiBuffer` 快照（锚点、语法树、折叠）。PF 没有这层包袱，**一次读盘就能把
「命中行 + 上下文行」一起收齐**，所以合并成单阶段，行为语义不变：

| Zed 语义 | PF 落点 |
|---|---|
| 路径候选尊重 .gitignore | `git ls-files --cached --others --exclude-standard`（与 @ 检索、文件搜索弹窗同源） |
| Scan Ignored = 连被忽略目录也扫 | `ignore::WalkBuilder` 四源全关 + 跳过 `.git` |
| include/exclude 前置于读盘 | `PathFilters::selected`，逐字移植 `SearchQuery::match_path` 的**向上逐级**判定 |
| 二进制早退（头 1KB） | `analyze_byte_content` + `ByteContent::Binary`（与文件编辑器同判据） |
| CRLF 容忍 | 逐行剥尾 `\r`（`regex` 没有 `fancy_regex` 的 `crlf(true)`） |
| 流式 + 路径序 | 后台按排序后的候选清单串行扫，逐文件回传（天然有序，无需 Zed 的乱序批次缓冲） |
| 上限 5000 文件 / 10000 命中行 | `MAX_FILES` / `MAX_MATCH_LINES`（同值），触顶发 `Limit`，计数后缀 `+` |
| 上下文 2 行、摘录合并 | `CONTEXT_LINES=2`；**相邻命中的重叠窗口并成一块**（Zed 按命中分 excerpt，PF 合并，避免同段代码重复出现） |

单线程串行是刻意取舍：`git ls-files` 十万级文件也是几十毫秒量级，磁盘随机读才是瓶颈；一旦并行，
就要引入 Zed 那套乱序批次重排，收益不抵复杂度（留作后续优化，`docs/agents/` 可记一笔）。

## 3. 产品级唯一差异：文件名与内容同面板

Zed 把「找文件」（Ctrl+P 文件查找器 / fuzzy）与「找内容」（Ctrl+Shift+F 项目搜索）做成两个
面板。PF 用户的心智是「一次输入、文件与内容一起搜」，因此**合并进同一个结果列表**：

- 文件名命中：用**同一套查询模式**测相对路径（`CompiledQuery::hits`），命中排在结果区最前的
  独立组里，文件头右侧标「文件名匹配」，`MAX_PATH_HITS = 50` 封顶（防 `src` 这类词把内容结果
  挤没）；点击即开文件首行。
- 内容命中：按路径序分组，文件头显示命中行数，摘录块逐行渲染。

严格说这是两套语义（fuzzy vs 正则）的取舍：文件名侧放弃 fuzzy 打分，换取「一个输入框、一套
模式、结果可解释」——输入 `main.rs`、`src/.*\.rs` 都能把目标文件捞出来，不需要第二个快捷键。

## 4. 面板版式（Zed `ProjectSearchBar::render` 逐行对照）

```
┌ 搜索条 ───────────────────────────────────────────────────────────┐
│ [查询输入框 ····················│ Aa  ab|  .*  ]  [筛][换]          │
│                                      [‹] [›] [1/23 ↻]             │
├ 替换行（替换钮开）────────────────────────────────────────────────┤
│          [替换为 ·················] [替换下一处][全部替换]          │
├ 过滤行（过滤钮开）────────────────────────────────────────────────┤
│          [包含 ·······] [排除 ·······]                    [忽略]  │
├ 错误 / 替换结果提示行（红字，按需出现）────────────────────────────┤
```

| Zed | PF | 说明 |
|---|---|---|
| query/replace/include/exclude = 内嵌 `Editor`（多行 + 语法高亮） | `TextInput`（单行，带 IME/剪贴板） | 查询语法高亮对普通用户无价值；统一输入件换来 IME 正确性 |
| `Aa` `ab\|` `.*` IconButton | `kit::text_toggle`（文字标签） | 整词没有现成图标语义，不为一个大写「ab」造 svg 资产 |
| 过滤/替换 IconButton | `kit::icon_toggle` | 新增页面级件，尺寸入 UI 组件规范 §10.4 |
| 计数 `1/23` + 触顶 `+` + 转圈 | 同 | |
| `SelectPreviousMatch/SelectNextMatch`（F3 / Shift+F3） | 条内 `‹`/`›` 钮（环绕） | 全局 F3 未绑（PF 快捷键表只登记动作键位，条内按钮够用） |
| `ToggleFilters` 不清输入 | 关过滤器 = **清空** include/exclude 并重搜 | 输入框隐藏后还留条件会让结果莫名变少，清掉更符合「关掉就是不要它影响」 |
| `ReplaceNext/ReplaceAll` | 同（脏缓冲跳过 + 计数回报） | PF 的文件缓冲有「磁盘真值 + 编辑器值」两层，写盘前先跳过有未保存修改的文件 |

## 5. 结果面板（Zed 多缓冲编辑器的视觉等价物）

Zed 把结果摆进 `MultiBuffer`：每个命中一个 excerpt、`Block::BufferHeader` 文件头、行号 gutter、
命中 range 高亮。PF 不复刻 multibuffer 内核（gpui-component 的 `InputState` 没有多缓冲/摘录/块
系统），只复刻**视觉结构与交互**：

| 元素 | 值 / 行为 |
|---|---|
| 文件组头 | 高 22、`bg_subtle`、上边 1px border；文件图标 14 + 文件名 11.5 SEMIBOLD + 目录 11 `text_faint` + 右侧计数 10.5 `text_dim`（文件名命中显示「文件名匹配」） |
| 摘录行 | 高 22、mono 11.5；行号 gutter 宽 44 右对齐（mono 10.5，命中行 `text_dim`、上下文 `text_faint`） |
| 命中高亮 | 命中区间 = accent 22% 洗底 + 正文 `t.text`（Zed primary range highlight 等价物） |
| 上下文行 | 同高、文字 `text_dim` + 整行 0.92 透明度（Zed excerpt 上下文同款） |
| 活跃命中 | 整行 accent 13% 洗底 + 左缘 2px accent 竖条（Zed 选中命中视觉），`‹›` 导航滚动到居中 |
| 列表 | 等高虚拟化（`vlist` + 单一 `ROW_H=22`），一万行只建视口内的行；右缘常显滚动条 |
| 点击 | 行 → 打开该文件 tab 并跳到行（`pending_jump` 由文件视图渲染帧消费 → `set_cursor_offset`）；文件头 → 打开首行 |

等高是刻意的：Zed 结果编辑器本身行高一致，用 `uniform_list` 换 O(1) 可见范围计算；分组感靠
底色与上边框而非高度差。

## 6. 数据流与生命周期

```
TextInput.on_change ──(250ms 防抖)──┐
开关/过滤器/替换动作 ───────────────┴─> Chat::search_start
                                          │ generation += 1（丢陈旧批次）
                                          │ cancel=true（旧循环尽快退出）
                                          ├─ background_spawn(run_search) ──> UnboundedSender<SearchMsg>
                                          └─ cx.spawn(前台泵)  <── 收拢批次（try_recv 排空）
                                                 └─ search_apply → rows(Arc<Vec<Row>>) → cx.notify
```

- **行模型跨帧复用**：`rows: Arc<Vec<Row>>`，追加走 `Arc::make_mut`，换代直接换新 `Arc`；
  渲染帧只克隆 `Arc`（零拷贝）——一万行的结果列表不会每帧深拷贝。
- **查询词镜像**：`SearchUi.query_text`（`on_change` 同步）。结果区空态判定、替换动作都不再读
  输入框实体，渲染路径零实体读。
- **状态住在 `WsUi.search`**（工作区级而非会话级）：切会话不丢，切项目后由 `open_project_search`
  重新发起。
- **tab 单例**：`PanelTab::Search` 在 `panel_tabs` 里至多一个；再按 Ctrl+Shift+F 只切过去并把
  焦点送回查询框（`focus_query` 请求位，渲染帧消费）。

## 7. 焦点（踩点）

搜索条输入框必须进 render 的**逐帧焦点仲裁白名单**（`Chat::search_input_focused`），否则每帧
都会被推回 composer/中性锚点，输入框点进去打不进字——与 040-1 市场搜索框、023 文件编辑器同一条
白名单纪律。`focus_query` 的消费点是「内件已建」才推焦点（`TextInput` 懒建，当帧推 fallback
句柄会造成焦点路径为空）。

## 8. 自动化（pif-ui）

面：`search`（`ui.snapshot` 的 `surface=search`）。

```json
{ "shown": true, "query": "fn main", "phase": "done", "opts": ["regex"],
  "show_replace": false, "show_filters": false,
  "files": 3, "path_files": 1, "matches": 12, "scanned": 428,
  "active": 0, "limit": false, "error": null, "notice": null,
  "row_count": 57, "row_h": 22,
  "rows": [ {"kind":"header","path":"src/main.rs","count":4,"path_only":false},
            {"kind":"line","line":12,"hit":true,"ordinal":0,"text":"fn main() {"} ] }
```

op：`search.open` / `search.query{text}` / `search.toggle{which}` / `search.step{forward}` /
`search.replace_all`。结果流式回填，断言照事务范式：`exec` → `wait --path search.phase --eq done`
→ `snapshot search`。
